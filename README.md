# IsosUI

IsosUI is the public source of the IsOS configuration graph editor. It is maintained independently of [IsOS](https://github.com/Island-Team/isos) and Island-web. IsOS owns the local API; Island-web hosts a pinned UI build. Both UIs connect to the IsOS process running at `127.0.0.1:16000`.

## Develop

Use Node.js 22 and npm 10 or newer:

```bash
npm ci
npm run dev
npm start
npm test
npm run build
```

`npm run dev` starts the standalone development frontend and `npm start` starts the standalone production-mode Webpack server. Both bind to `127.0.0.1:16001` and call IsOS at `http://127.0.0.1:16000/api/isos/v1` and EOS at `http://127.0.0.1:16020/api/eos/v2`. To use different loopback ports, set `ISOSUI_PORT`, `ISOSUI_API_ORIGIN=http://127.0.0.1:<api-port>`, and `ISOSUI_EOS_API_ORIGIN=http://127.0.0.1:<eos-port>` before launching npm. API origins are embedded when Webpack compiles the frontend; only HTTP loopback origins are accepted. IsOS and EOS allow the frontend's exact origin in CORS. The editor uses no URL token or Authorization header.

For an IsOS-managed workbench, build the bundle in this repository, configure IsOS to use `dist/local`, then run `isos serve`:

```bash
npm ci
npm run build
isos serve
```

`npm run build` creates local and hosted bundles. Configure IsOS with the prebuilt local bundle directory; `isos serve` verifies and serves that bundle at `127.0.0.1:16001`. Core repositories own their own builds, and IsOS uses configured binary directories. In dev mode, `ISOSUI_REPO_PATH="$PWD" isos serve --ui-live` explicitly supervises `npm start` instead. Stop IsOS-owned listeners with `isos stop` or Ctrl+C in the `isos serve` terminal. Stop a separately launched npm server in its own terminal before starting IsOS on the same port.

## Workbench

The node graph editor is the only IsOS configuration editor. It reads and saves the current `/node-graph` contract through the shared IsOS API client; the retired `/graph` and `/profiles` editor is no longer included in either bundle. IsosUI's first release version is `1.0.0`; IsOS uses API v1 and graph format `1.0.0`. The EOS bridge keeps its independent API v2 contract.

Home, Graph, and EGIA log panels read the unified IsOS `/api/isos/v1/logs` endpoint with a cursor. Home opens **All sources** by default, including when no process is running; the source menu can narrow the view to a specific process. The panel also retains browser console, error, and graph-canvas events for the current page session. **All sources** combines those browser entries with IsOS manager events, service logs, EOS, and other sources; **Browser** isolates client events. The display level defaults to info and above; changing it filters the buffered entries in the browser without changing what IsOS records. Selecting another source starts its cursor from the beginning, and log rotation clears the previous stream. Follow pauses polling when unchecked or while the page is hidden.

The workbench has Home, Graph, EOS, and EGIA pages. Home can install a package by exact ID and version or link a local bundle with an optional absolute release manifest path, even when the graph has no package node yet. Omitting the manifest path lets IsOS discover `release.json` in the bundle root. Home lists all installed package receipts from `/packages` and shows backend readiness separately from `/backends`. It shows setup checks, saved and active revisions, process states, run/restart/stop actions, and bounded logs. EOS presents controls only for manual, primitive, and skill nodes declared in the active graph; EGIA provides an IsOS-backed Overview and Logs workbench; it reports when no EGIA process is available. Graph reads the one authored node graph from IsOS `/api/isos/v1/node-graph` and the registered type catalog from `/api/isos/v1/node-types`. A type fixes its core, layer, group, lifecycle, configuration fields, and typed ports. Adding a node creates an instance under that type's placement. The current type definitions use `@v1.0`; the graph format is `1.0.0` and IsosUI keeps its independent app version.

Installed package node sets appear in the library from IsOS `/node-sets`. Select a set, enter any string parameters, and preview through `/node-sets/preview`; the server returns the composed graph and added paths without saving. Add stages that preview as one undoable graph edit. A package preview must preserve existing nodes. If a preview would remove nodes, the editor rejects it; edit the graph explicitly before adding the new set. Check graph and Save graph use the revision-checked graph API. Older IsOS builds without node-set endpoints show an empty set library.

Select an instance to edit its identity, label, description, capabilities, and typed settings. The backend package, version, scene, and device choices come from IsOS `/backends` when available. IsOS `/node-options` supplies available adapter families and hardware targets for the current draft; the `/node-types` catalog supplies primitive names, versions, and movement types. Generic `eos.hardware.*` nodes choose `node.adapter.type`. `eos.dispatcher.primitive_base@v1.0` and `eos.dispatcher.primitive_manipulator@v1.0` binding nodes choose an exact primitive and one target through the hardware command edge, without a duplicate target setting. Instance paths use `<core>/<layer>/<group>/<node>`; old expanded paths remain readable during migration. Hardware fields have an advanced JSON editor for adapter, frame, observation, and safety bounds. Manual and primitive nodes have a target hardware picker; a primitive also selects one supported movement mode. Skill nodes have an ordered primitive picker. These controls keep the dispatcher reference and typed observation/status inputs synchronized with the selected hardware and steps. Search the type library, double-click the canvas to add a type, and drag an output port to a matching input port. Inputs accept one provider unless their registered port declares `cardinality: many`; hardware command inputs can receive multiple primitive bindings. Left-drag a blank canvas area to select multiple nodes, middle-drag to pan, and right-click to open quick add or disconnect a wire. Ctrl+Z/Ctrl+Y undo and redo graph edits; Delete removes all selected nodes. The primary Graph action validates, saves an edited draft, and runs or restarts its exact revision. The Advanced menu has Check graph, Save graph, and Reload saved graph. Check graph reports problems without saving. Save graph validates, saves, and generates core configuration. Reload saved graph discards local edits after confirmation. Core readiness shows the configured path, reported version, compatibility, graph configuration, running state, and the reason and next action when blocked. Home will not run or restart while the current editor has unapplied changes. Refresh asks before discarding local edits. Saving a snapshot preserves edits made while the request is in flight. Canvas positions are saved per robot graph in local browser storage and remain separate from graph data. Standard desktop controls are about 30 px high; touch controls are at least 44×44 px.

The EOS MuJoCo process inspector supports the package-owned `eos.process.mujoco@v1.0` type and legacy backend type. Scene choices and Home package readiness use the exact `node.package` pin for the new type; legacy settings remain readable. The inspector has a **Show MuJoCo window** setting. It writes `MUJOCO_GUI=1` in that backend node's environment map. Apply the graph and start or restart EOS to show the simulation instance EOS supervises. The simulator remains headless when the setting is off.

Node top borders identify the registered layer; a deterministic shade within that layer identifies the group, including package groups such as `mujoco`. The palette gives process, hardware, dispatcher, control, and EGIA common/data layers stable hues; other layers receive a stable hash-based hue. Five bounded group shades are selected by group name, with light and dark variants. Core, hardware kind, and exact package version appear as card badges. Error outlines and runtime status remain separate from graph identity. Anchor shape represents transport (in-process circle, Unix socket square, WebSocket diamond, ROS 2 hexagon); anchor color identifies the exact payload data type. Line pattern represents declared frequency from sparse low-rate dots to solid high-rate lines, while unknown rates use dashes. Line color remains neutral until priority semantics are defined. Wire data labels appear on hover, keyboard focus, or selection. The canvas shows brief configuration summaries and never renders live payloads as node settings.

The graph is configuration, not live camera or movement data. IsOS applies a saved revision to managed processes on restart. EOS forms use the saved revision only when it matches the active revision. Manual and primitive calls supply typed movement data for the graph-declared target; skill calls supply typed step data for the graph-declared primitive sequence. EOS validates the node identity, mode, limits, and dispatcher route. Manual Stop and skill Cancel resolve through those graph nodes. The monitor shows only declared hardware discovered by EOS and polls adapter status, health, and observations every 2 seconds. The adapter status drives Live, Stopped, Starting, Fault, and Stale badges; health remains a separate reading. A failed poll retains the last observation with an error and its update time. Camera cards omit observation fields.

**Graph workbench and Vision.** Save and Run validates and saves ordinary graph edits with revision checking, generates core configuration, then starts the applied graph. Restart reloads the verified configured binaries and graph revision. Errors appear as inline alerts; successful operations appear as plain note lines. Home checks a local bundle manifest before linking, fills package ID and version from the preview, and shows verification issues. Home also reports core build and launch readiness. The View menu toggles the library, inspector, diagnostics, and live log panel, and opens EOS or EGIA in a docked or floating graph window. Drag the window header to float it, resize it at the lower corner, maximize it, or restore it. Layout is local to this browser. EOS shows its runtime workbench; EGIA shows IsOS process status and logs while its core-specific runtime API is unavailable. Right-click Add Node shows registered type details on hover or keyboard focus. `R` mirrors selected nodes visually to inputs on the right and outputs on the left without changing the graph. Clicking an edge shows the catalog's readable payload IDL and units. The editor legend explains transport shape, exact data type color, and frequency pattern. Wire color stays neutral and wires do not animate.

The EOS Vision section lists active compatible camera gates from `/api/eos/v2/vision/gates`. The `preview` input of the IsOS-owned `isos.ui.vision@v1.0` node (`isos/ui/panel/<id>`; the old `isosui.system.vision@v1.0` ID remains a migration alias) selects a gate and opens its read-only `/api/eos/v2/vision/ws` stream automatically when the saved and active graph revisions match. The subscription carries that exact revision and the Vision node's optional FPS, width, and JPEG quality settings. An unlinked Vision input requires manual source selection; a stale graph or mismatched EOS catalog blocks subscription with an inline reason. The panel shows delivered FPS, dimensions, connection state, and errors. A dropped stream retries at bounded intervals up to five times; Retry resumes it, while Disconnect leaves it closed. Switching source closes the previous socket. Each binary frame is bounded to an 8 MiB JPEG plus metadata and carries length-prefixed JSON metadata followed by JPEG bytes. Browser loopback permission may be required for a hosted HTTPS page. The UI is served by foreground `isos serve` from its configured bundle and does not require a user service.

## Build contract

| Command | Output | Asset base | API base |
| --- | --- | --- | --- |
| `npm run build:local` | `dist/local/` | `/` | IsOS `http://127.0.0.1:16000/api/isos/v1`, EOS `http://127.0.0.1:16020/api/eos/v2` |
| `npm run build:hosted` | `dist/hosted/` | `/isosui/` | IsOS `http://127.0.0.1:16000/api/isos/v1`, EOS `http://127.0.0.1:16020/api/eos/v2` |

Each output has `index.html`, `assets/`, `IslandTeam.png`, and `manifest.json`. The manifest declares `schema_version: 1`, `version`, `source_commit`, `api_schema_version: 1`, and `build_target`. The standalone npm server and IsOS's configured static server serve `/en/isos` and `/cn/isos` locally. Island-web places hosted assets under `/isosui/` and copies the hosted HTML to its `/en/isos` and `/cn/isos` static routes so URL fragments remain intact.

The manual release workflow accepts an existing `v<package version>` tag. It builds both targets and publishes `isosui-local-<tag>.tar.gz`, `isosui-hosted-<tag>.tar.gz`, and `SHA256SUMS`. A release is not required to develop or build from a pinned source commit. After publishing, it dispatches an `isosui-release` event to Island-web. Configure a fine-grained token for `Island-Team/Island-web` with Contents write access as `ISLAND_WEB_DISPATCH_TOKEN` in IsosUI. Island-web verifies the hosted archive, builds the pinned website, and opens a PR; squash merge that PR after checks pass to trigger the normal website deployment.
