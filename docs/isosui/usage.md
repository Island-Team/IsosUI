# First use: graph and workbench

[中文](../../docs_cn/isosui/usage_cn.md) · [Design](design.md) · [TODO](todo.md)

## Current path

1. Install Node.js 22 and npm 10, then run `npm ci` and `npm run build` in this repository. Select the resulting `dist/local` build in IsOS. Alternatively, `npm run dev` starts the standalone frontend on `127.0.0.1:16001`; the IsOS and EOS loopback APIs must be running for graph and live controls.
2. Start IsOS with `isos serve` and open `/en/isos` or `/cn/isos`. Home shows manager setup, installed package receipts, core readiness, process state, and all-source logs. An offline API is an explicit blocked state, not an empty graph.
3. Install or link the exact `island/mujoco-sim@0.1.1` package in IsOS. In Graph, choose the installed `sim-hardware` node set, preview its additions, and select a scene. The current editor obtains scenes from `/backends` and device/adapter choices from `/node-options`; its package choices are not yet a general asset selector.
4. Select each node to read its description and configure its type-defined fields. Connect compatible output and input ports, then choose **Check graph** under Advanced. If a wire is highlighted, select it: the inspector shows source and destination type IDs, IDL field units, and any IsOS rejection code, path and reason for that input. The Diagnostics section retains the full server result. Correct the port or node setting and check the graph again; a draft edit makes the previous result stale. The inspector's deployment state is separate from live node health, which opens in the EOS monitor. Use the primary Graph action to save and run only after the check is clear. The server validates and applies the graph; a browser draft alone does not control EOS.
5. Wait for Home readiness, then open EOS controls and monitor. Controls appear only for declared nodes in the active graph. The current Graph View menu can float a combined EOS or EGIA window; Vision and the control/monitor/log sections are not independent floating panels yet.
6. To find a failure before launch, open Home Logs. Its pinned manager-session anchor shows the first package or Apply failure even when detail filters hide that source. After launch, the panel pins the run's first ready or failure event. Filter later detail rows by source, level, node path or correlation ID; the anchor remains visible. Copy the run ID and correlation ID into the EOS or EGIA investigation. Home status supplies live readiness and the saved/active revision; a stale active revision blocks live control.
7. Stop the deployment with IsOS. For an upgrade, install a new exact package version, preview its nodes, check the graph, apply a new revision, and restart. Retain the previous graph and package receipt for recovery.

The root [README](../../README.md) gives the actual development commands, API origins and build outputs. IsOS owns package installation and process operations.

## P07 log navigation

Open Home Logs after a package or Apply failure. The panel asks IsOS for `view=current` and shows the manager-session first package/Apply failure above the source, level, node and correlation filters. While no such event has arrived, it says the anchor is pending; an empty list is not evidence of success. After IsOS admits a deployment run, the panel switches to that run's first ready or failure event, then shows later detail rows. It keeps that run selected after Stop, process exit or manager restart until IsOS admits another run. Use Home status for live readiness and the saved/active revision; the log event explains what happened at its own time.

Pause Follow to inspect a row's safe source, core, event code, run ID, correlation ID and graph node pointer. Narrow the detail rows only after seeing the pinned first event. If retention or rotation lost entries, the panel displays a gap notice and resumes in the same run; if the collector is unavailable, it retains the last rows and cursor and displays an error until recovery. A new admitted run gets a visible boundary and its own anchor. Browser console diagnostics remain separate from IsOS events. The P07 panel displays owner-reported event identity and preserves a legacy compatibility view when IsOS lacks the opt-in response. See the [P07 UI contract](interfaces/log-cursors.md).

An empty filtered page with an advancing cursor and no diagnostic means no matching detail row yet; it is not a gap. If status reports `run_id_state:unavailable` or current logs return `log_scope_unavailable`, keep prior rows marked stale and use live status while IsOS recovers the run identity. A `log_scope_publish_failed` Run error means no child was spawned, but the durable run record may have survived; refresh status and current logs before interpreting the scope. Neither condition authorizes the UI to choose a manager session or declare readiness.

## Target interaction — planned

Graph starts with a searchable registered type library. A selected type shows its nonblank **type description**, placement, capabilities, port contract and setting help; a selected instance shows its own editable description. The configuration form renders settings from catalog metadata. A selector, like a model-weight picker, searches verified options for that **node and setting**; scene and device options ship first. The selector header shows the exact package/version pin; each option row shows stable ID, human label, description, availability and reason. Keep an unavailable saved value visible with its reason; never silently replace it. Check graph remains available and reports unresolved or invalid choices; Apply is blocked until they are corrected. Package paths stay private to IsOS; the graph saves stable IDs and exact package pins.

Hover or keyboard-focus a node to open an info card beside the pointer on hover or the node on focus, above neighboring nodes. Show registered type description and instance description separately, plus placement, ports and units; show live health only when reported by its owning core. Clamp the card inside the viewport, make it available on touch, and keep dragging and wire editing usable.

Each wire exposes `priority` (nice `-20..19`, default `0`) and optional `frequency_hz` (positive finite delivery cap). The inspector edits them against an IsOS validation result. Labels show both values at normal zoom and in keyboard focus text; the legend explains priority and frequency separately from transport and payload type. A wire without an active runtime route is explicitly **design only**. Priority affects scheduling, never dispatcher safety admission.

The workspace docks or floats **control**, **monitor**, **Vision**, and **logs** independently. A floating panel has a drag handle, resize handle, focus order, close/dock action, bounded viewport, and local layout persistence. When reopening, clamp saved geometry to the viewport. On a narrow screen, stack panels and preserve Stop, connection failure and stale-revision indicators. Work pages use compact aligned rows and transparent or lightly translucent surfaces; visual overview pages may use wider spacing. Both share Island-web-inspired tokens, restrained borders, visible keyboard focus, 28–30 px desktop controls and at least 44×44 px touch targets.

For the first primitive demo, inspect a node, check and apply its graph, then wait for EOS readiness. In the EOS control panel select one active primitive binding and inspect its single graph-resolved target; changing that target requires a graph edit and Apply. The panel shows both node descriptions and the typed primitive fields from the owner contract. Invoke through the existing loopback `primitive_typed` bridge. Show browser-local sending, then the exact `Completed`, `Cancelled`, `Rejected`, `InProgress` or `OutcomeUnknown` status from the correlated response; `InProgress` stays open until a future authorized result read confirms an outcome. Show the related run log and live health separately. A graph edge alone never means the command ran. Stop through the existing deployment control. This is planned UI behavior, not a currently available control flow.
