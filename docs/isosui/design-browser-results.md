# R07 browser result client and workbench state

[中文](../../docs_cn/isosui/design-browser-results_cn.md) · [UI contract](interfaces/browser-results.md) · [First use](usage.md)

**Design only on this branch.** The current `src/services/eos/control.ts` exports a generic `eosRequest`; `EosWorkbench.tsx` still renders legacy `manual`, `primitive` and `skill_*` controls with a JSON string as the last result. It has no typed `primitive_typed` sender or authorized `result` reader. This R07 design adds a typed result service and state reducer for the future U04 active-binding control, without making the legacy controls an alternate movement route. The [EOS owner R07 contract](interfaces/browser-results.md) fixes the wire and errors; IsOS owns revision/run/Stop.

## Client and state boundary

Add a focused `src/services/eos/primitive-result.ts` client built on the existing validated loopback origin and request options. It accepts only `{commandId, activeRevision}`, produces exactly the three public JSON keys `op`, `command_id`, `active_revision`, parses the six-status `DispatchResult`, verifies the returned command ID, and maps bounded transport/owner/protocol errors to a discriminated result. Keep private grant and raw routes out of its type. Do not teach components to call `fetch` directly. A rejected HTTP or `ok:false` envelope is an error; it is never coerced to a `Rejected` command status. A service timeout or malformed success is unavailable, not `OutcomeUnknown`, because only EOS can assign that command status.

Add `src/components/isos/primitive-result-state.ts` as a pure transition model consumed by `EosWorkbench`. A record contains the captured IsOS `runId`, `activeRevision`, active binding path, generated `commandId`, last owner `DispatchResult` or null, browser phase (`sending`, `following`, `terminal`, `paused`, `unavailable`), last safe error and request generation. The only transition into `terminal` comes from a correlated EOS status in `Completed`, `Failed`, `Cancelled`, `Rejected` or `OutcomeUnknown`; `InProgress` remains `following` or `paused`. Store a `Failed` result separately from `Rejected` and a transport error. Keep the command ID visible across errors. Never start a second `primitive_typed` send from a timeout or uncertain result.

Before U04 sends a typed command it must resolve one active graph binding and target, check `saved_revision === graph.revision === active_revision`, `run_id_state:known`, `state:running`, clean draft and EOS readiness. Capture the run/revision/binding/ID once. The result state model re-reads IsOS `process-status` immediately before each follow-up and after a page becomes visible; it compares current `run_id` and revision with the captured values. An IsOS status error or `run_id_state:unavailable` pauses follow-up as unavailable. A stopped run, changed run or changed revision aborts the pending read and seals that record as old-run/unavailable. A browser request generation and `AbortController` prevent a late reply after selection, Stop, unmount or run change from updating the current card. A fresh command gets a fresh record even if the same binding is selected. The UI must not derive the active revision from a draft or from the command response.

The result poll is one read at a time, with the 1-second initial delay, 10-second maximum error backoff, 60-second/12-attempt bound and hidden-tab pause in the UI contract. `InProgress` remains visible when the bound expires; manual Refresh rechecks IsOS before one read. A terminal status stops reads. If the first send response is lost, the UI may perform only this guarded result read using the generated ID, accepting `unknown command ID` as opaque unavailability. The service never retries `primitive_typed`. Vision keeps its separate read-only WebSocket and revision fence. The result card shows command ID, active revision, binding path, exact owner status or unavailable explanation, last update, and a current-run log link/filter by correlation ID; it never uses a Graph edge animation as proof of release.

## Integration with the existing workbench

The existing `EosWorkbench` five-second IsOS status refresh can supply a visible revision warning, but a follow-up must obtain a fresh process status just before each request; cached React state is insufficient. The generic `eosRequest` currently throws an undifferentiated message for non-2xx responses, so the new typed reader needs explicit safe classification while retaining the same validated origin, CORS mode and no credentials. Keep the command card mounted and labeled unavailable if the bridge fails; do not clear it by `setResult('')` on a background refresh. Render the six statuses as text and `role=status` or `role=alert` where appropriate, with Chinese and English copies. `Failed`, `Rejected`, `OutcomeUnknown`, an opaque old ID, and bridge outage need distinct text; color alone cannot carry meaning. Keep a persistent IsOS Stop button or link in the EOS panel, backed by `controlProcesses('stop')`, outside the EOS bridge and independent of `active`, graph editability, and result-poll state. Show IsOS's returned stop status; R06 owns its physical stop receipt. The full active-binding list, typed argument form, info card and panel layout remain U04/U03 work.

## Review and verification gate

The [fixture matrix](../../tests/fixtures/browser_results/cases.json) freezes request, owner-result, run/revision, outage and Stop transitions. Implementation tests should use a stubbed EOS bridge and IsOS status service to verify exact public body, no grant, all six statuses, a late reply after run change, initial send timeout without movement retry, one-in-flight bound, hidden-tab pause, 60-second bound, `unknown command ID` opacity, bridge 502/503, stale revision, malformed result and IsOS Stop availability. A browser component test must prove Stop stays reachable when EOS is offline and active revisions differ. Both local and hosted builds must pass `npm test` and `npm run build`. The cross-owner first-use replay must use a real IsOS saved/active run, EOS bridge and `InProgress` follow-up, then stop and inspect the current-run log; R07 and U04 remain open until that evidence and independent implementation review pass.

For this design revision, `python3 tests/fixtures/browser_results/check.py` passes 32 unique cases and all six statuses, a relative-link check passes six EN/CN design and fixture pages, and `git diff --check` passes. Complete command output is in ignored `logs/test/20261102-r07-isosui-design/`. Independent design review remains required before implementation.
