# R07 browser result client and workbench state

[中文](../../docs_cn/isosui/design-browser-results_cn.md) · [UI contract](interfaces/browser-results.md) · [First use](usage.md)

**Design only on this branch.** The current `src/services/eos/control.ts` exports a generic `eosRequest`; `EosWorkbench.tsx` still renders legacy `manual`, `primitive` and `skill_*` controls with a JSON string as the last result. It has no typed `primitive_typed` sender or authorized `result` reader. R07 adds one minimal active-binding typed sender, a correlated result reader and a state reducer; U04 later expands the complete per-binding UI. The legacy controls cannot become an alternate movement route. The [EOS owner R07 contract](interfaces/browser-results.md) fixes the wire and errors; IsOS owns revision/run/Stop.

## Client and state boundary

Add `src/services/eos/primitive-command.ts` for a narrow `base.velocity` sender and `src/services/eos/primitive-result.ts` for the guarded read, both using the existing validated loopback origin and request options. The sender takes an active resolved binding, its one graph-edge target, active revision, checked `body_velocity` arguments, EOS monotonic time, positive sequence and fresh command ID; it produces exactly the public `primitive_typed` envelope, computes `payload_length_bytes` with `TextEncoder` over compact JSON, and rejects non-safe clock/deadline numbers. It never accepts a free-form target or private grant. The result client accepts only `{commandId, activeRevision}`, produces exactly the three public JSON keys `op`, `command_id`, `active_revision`, parses the six-status `DispatchResult`, verifies the returned command ID, and maps bounded transport/owner/protocol errors to a discriminated result. Both clients use one decoder so the initial send and follow-up have identical status semantics. Do not teach components to call `fetch` directly. A rejected HTTP or `ok:false` envelope is an error; it is never coerced to a `Rejected` command status. A service timeout or malformed success is unavailable, not `OutcomeUnknown`, because only EOS can assign that command status.

Add `src/components/isos/primitive-result-state.ts` as a pure transition model consumed by `EosWorkbench`. A record contains the captured IsOS `runId`, `activeRevision`, active binding path, generated `commandId`, last owner `DispatchResult` or null, browser phase (`sending`, `following`, `terminal`, `paused`, `unavailable`), last safe error and request generation. The only transition into `terminal` comes from a correlated EOS status in `Completed`, `Failed`, `Cancelled`, `Rejected` or `OutcomeUnknown`; `InProgress` remains `following` or `paused`. Store a `Failed` result separately from `Rejected` and a transport error. Keep the command ID visible across errors. Never start a second `primitive_typed` send from a timeout or uncertain result.

R07 renders one minimal active base binding card with its graph-resolved target and four bounded SI fields; the operator clicks Invoke. This card is available for a mock adapter qualification without opening MuJoCo movement before R06. Before sending it resolves the exact active graph binding and target, checks `saved_revision === graph.revision === active_revision`, `run_id_state:known`, `state:running`, clean draft, EOS readiness and owner-reported target movement availability. Capture the run/revision/binding/ID once, obtain EOS monotonic time, recheck the IsOS fence immediately before send, then submit once. The result state model re-reads IsOS `process-status` immediately before each follow-up and after a page becomes visible; it compares current `run_id` and revision with the captured values. An IsOS status error or `run_id_state:unavailable` pauses follow-up as unavailable. A stopped run, changed run or changed revision aborts the pending read and seals that record as old-run/unavailable. A browser request generation and `AbortController` prevent a late reply after selection, Stop, unmount or run change from updating the current card. A fresh command gets a fresh record even if the same binding is selected. The UI must not derive the active revision from a draft or from the command response.

The result poll is one read at a time, with the 1-second initial delay, 10-second maximum error backoff, 60-second/12-attempt bound and hidden-tab pause in the UI contract. `InProgress` remains visible when the bound expires; manual Refresh rechecks IsOS before one read. A terminal status stops reads. If the first send response is lost, the UI may perform only this guarded result read using the generated ID, accepting `unknown command ID` as opaque unavailability. The service never retries `primitive_typed`. Vision keeps its separate read-only WebSocket and revision fence. The result card shows command ID, active revision, binding path, exact owner status or unavailable explanation and last update. It links to unfiltered current-run logs unless an EOS owner event supplies a valid matching `correlation_id`; then it may prefill that filter. It never assumes the command ID is a log correlation ID or uses a Graph edge animation as proof of release.

## Integration with the existing workbench

The existing `EosWorkbench` five-second IsOS status refresh can supply a visible revision warning, but a follow-up must obtain a fresh process status just before each request; cached React state is insufficient. The generic `eosRequest` currently throws an undifferentiated message for non-2xx responses, so the new typed clients need explicit safe classification while retaining the same validated origin, CORS mode and no credentials. Keep the command card mounted and labeled unavailable if the bridge fails; do not clear it by `setResult('')` on a background refresh. Render the six statuses as text and `role=status` or `role=alert` where appropriate, with Chinese and English copies. `Failed`, `Rejected`, `OutcomeUnknown`, an opaque old ID, and bridge outage need distinct text; color alone cannot carry meaning. Put an IsOS Stop action beside the R07 card, backed by `controlProcesses('stop')`, outside the EOS bridge and independent of `active`, graph editability, and result-poll state. Show IsOS's returned stop status; R06 owns its physical stop receipt. The full active-binding list, rich typed argument forms, info card and floating panel layout remain U04/U03 work.

## Review and verification gate

The [fixture matrix](../../tests/fixtures/browser_results/cases.json) freezes typed send, result read, owner-result, run/revision, outage, log-link and Stop transitions. Implementation tests should use a stubbed EOS bridge and IsOS status service to verify exact public bodies, no grant, one active binding/target, payload byte length, safe monotonic deadline, all six statuses, a late reply after run change, initial send timeout without movement retry, one-in-flight bound, hidden-tab pause, 60-second bound, `unknown command ID` opacity, bridge 502/503, stale revision, malformed result and IsOS Stop availability. A browser component test must prove Stop stays reachable when EOS is offline and active revisions differ. Both local and hosted builds must pass `npm test` and `npm run build`. The cross-owner first-use replay must use a managed mock-adapter IsOS saved/active run, EOS bridge, a real `primitive_typed` response and `InProgress` follow-up, then Stop and inspect current-run logs. Real MuJoCo movement remains R06-gated. R07 and U04 remain open until their own evidence and independent implementation reviews pass.

For this revised design, `python3 tests/fixtures/browser_results/check.py` passes 46 unique send/read/state cases and all six statuses; a relative-link check passes 12 changed EN/CN design and fixture pages; `git diff --check` passes.
